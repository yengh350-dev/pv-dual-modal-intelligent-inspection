# 信息架构与任务流

## 设计目标

平台以“完成一次可追溯的巡检处置”为主线，而不是按技术名词堆放页面。一级导航只承载稳定业务域；临时动作、跨域跳转和低频设置进入命令面板、页面工作栏或抽屉，避免继续增加主导航。

## 五类业务域

| 业务域 | 页面 | 使用目的 |
| --- | --- | --- |
| 作业运行 | 指挥大屏、作业总览、任务与航线、实时飞行 | 计划、执行和监看一次巡检任务 |
| 识别处置 | 双模态证据、异常中心、运维工单 | 从模型候选进入人工复核，再形成处置闭环 |
| 资产成果 | 资产档案、报告中心 | 沉淀组件历史并输出可审计成果 |
| 算法数据 | 模型实验、数据管理 | 管理训练数据、模型版本、指标和适用边界 |
| 系统管理 | 用户与权限、集成与设置 | 管理人员、角色、外部连接和系统诊断 |

## 主流程

任务与航线 → 实时飞行 → 双模态证据 → 异常中心 → 运维工单 → 资产档案 → 报告中心。

页面工作栏中的“下一步”只连接这个主流程，不代替页面自己的专业操作。任何 AI 结果都先进入证据或异常队列，不直接生成工程故障结论。

## 功能取舍

- 保留“指挥大屏”和“作业总览”：前者面向实时态势和调度，后者面向任务、质量与待办汇总，职责不同。
- 合并概念而不合并证据：资产与报告同属成果域，但仍保留独立页面，避免报告生成逻辑污染资产台账。
- 模型与数据同属算法域：数据版本、训练实验和指标必须能够相互追溯。
- 不新增“AI 中心”：AI 助手是全局工具，模型实验是受控研发页面；单独增加一级入口会造成职责重复。
- 不新增孤立驾驶舱：新增图表必须回答风险、质量、效率或资源问题，并能跳转到对应明细。

## 交互约定

- 导航分组可折叠，并在本机保存状态；当前页面所在分组会自动展开。
- `Command/Ctrl + K` 打开统一工作启动器，可按“热斑、工单、导入、模型”等自然词搜索。
- 带查询参数的快捷入口必须触发真实筛选或抽屉，不允许只有 URL 变化。
- 移动端只保留作业运行四个高频入口，其余功能通过搜索和页面内操作进入。

## 后续扩展规则

新增功能先判断归属：高频、稳定、跨任务使用的页面才进入一级导航；单次任务动作放在页面工具栏；对象详情放在抽屉；跨页面动作放在命令面板。若新功能与现有页面解决同一个用户问题，应优先扩展现有页面，而不是新增模块。
